# Конст пати

## Назначение и состояние

Конст пати (КП) - постоянная группа персонажей одной игры и одного сервера. Пользователь создает КП от имени своего персонажа; выбранный персонаж становится лидером.

Реализованы:

| Возможность | Состояние |
|---|---|
| Создание и список КП | Включено |
| Состав, роли и передача лидерства | Включено |
| Поиск персонажей и приглашения | Включено |
| Уведомления об изменениях состава | Включено |
| Хранилище и история выдач | Включено |
| Неизменяемый журнал действий | Включено |
| Роспуск КП с полным удалением данных | Включено |
| Realtime-чат | Реализован, но отключен feature flag |

## Навигация и страницы

В меню пользователя на аватаре находится пункт **Мои КП** с подсказкой **Мои конст пати**.

| Страница | Назначение |
|---|---|
| `/my-constant-parties` | КП текущего пользователя и входящие pending-приглашения |
| `/my-constant-parties/create` | Создание КП и выбор персонажа-лидера |
| `/constant-parties/:id` | Состав, приглашения, хранилище, история и логи КП |

В карточке КП на странице **Мои КП** отображаются название, сервер, количество участников и ник лидера. Во входящем приглашении показываются КП, приглашенный персонаж, отправитель и необязательное сообщение.

Основные вкладки страницы КП:

| Вкладка | Доступность |
|---|---|
| **Состав** | Все участники |
| **Хранилище** | Все участники; изменение только при наличии права |
| **Приглашения** | Лидер и участники с правом управления хранилищем |
| **Логи** | Все участники; вкладка расположена последней |
| **Чат** | Скрыта, пока чат отключен feature flag |

Кнопка возврата перед названием КП остается доступной при прокрутке страницы.

## Привязка к игре и серверу

КП хранит `game_id`, `localization_id` и `server_id`, полученные от персонажа-лидера.

Список КП, входящие приглашения, доступные персонажи-лидеры и прямой просмотр фильтруются по игре сайта, открытого пользователем. При создании переданный `game_id` должен совпадать с игрой выбранного персонажа. Открытие КП другой игры в текущем игровом контексте возвращает `404`.

Все активные участники находятся на сервере КП. Персонаж не может одновременно состоять в двух активных КП.

Основные запросы игрового контекста:

```http
GET  /api/v1/constant-parties?game_id={game}
GET  /api/v1/constant-parties/{constant_party}?game_id={game}
POST /api/v1/constant-parties
```

## Создание КП

Авторизованный пользователь выбирает принадлежащего ему персонажа текущей игры и задает название КП. Создание выполняется в транзакции:

1. Проверяется владелец, игра и отсутствие другого активного членства.
2. Создается КП с игрой, локализацией и сервером персонажа.
3. Персонаж добавляется в состав с ролью `leader`.
4. Лидеру автоматически выдается `can_manage_storage=true`.
5. В журнал записывается вступление с источником `party_created`.

## Состав и права

### Роли

| Возможность | Лидер | Управляющий хранилищем | Обычный участник |
|---|:---:|:---:|:---:|
| Просматривать состав и историю предметов | Да | Да | Да |
| Просматривать хранилище и логи | Да | Да | Да |
| Добавлять, изменять и удалять предметы | Да | Да | Нет |
| Выдавать предметы и отменять выдачу | Да | Да | Нет |
| Искать персонажей и отправлять приглашения | Да | Да | Нет |
| Просматривать и отзывать приглашения | Да | Да | Нет |
| Назначать права хранилища | Да | Нет | Нет |
| Исключать участников | Да | Нет | Нет |
| Передавать лидерство | Да | Нет | Нет |
| Распускать КП | Да | Нет | Нет |

Признак права управления хранилищем отображается рядом с персонажем в составе.

### Отображение состава

Фильтры расположены в порядке **Активные**, **Неактивные**, **Все персонажи**. По умолчанию выбран фильтр **Активные**. Количество персонажей показывается рядом с заголовком **Персонажи**.

При выборе персонажа справа отображается его история полученных предметов. Доступны поиск по названию предмета и выбор диапазона дат одним date range picker.

Бывшие участники находятся ниже активного состава и отображаются приглушенно. Их история выдач остается доступной. Если персонаж снова вступил в ту же КП, он показывается только среди активных участников.

### Управление участниками

```http
PATCH  /api/v1/constant-parties/{constant_party}/members/{member}
DELETE /api/v1/constant-parties/{constant_party}/members/{member}
POST   /api/v1/constant-parties/{constant_party}/members/{member}/transfer-leadership
```

Лидер может изменить `can_manage_storage`, исключить участника или передать ему лидерство. Эти действия доступны из меню выбранного участника.

Обычный участник может самостоятельно покинуть КП кнопкой **Покинуть КП**. Лидер не может выйти, пока не передаст лидерство или не распустит КП.

Передача лидерства выполняется в транзакции. Новый лидер получает роль `leader` и право управления хранилищем. Предыдущий лидер становится обычным участником без этого права. Новому лидеру отправляется уведомление.

## Приглашения

### Поиск и отправка

Кнопка **Пригласить** открывает модальное окно. Персонаж выбирается по нику, ID вручную не вводится.

Поиск выполняется во время ввода:

| Правило | Значение |
|---|---|
| Минимальная длина | 2 символа |
| Debounce frontend | 300 мс |
| Максимум результатов | 10 |
| Сервер | Только сервер КП |
| Исключения | Активные участники, персонажи другой КП и уже приглашенные pending-персонажи |

```http
GET  /api/v1/constant-parties/{constant_party}/invitations
GET  /api/v1/constant-parties/{constant_party}/invitations/candidates?query=ник
POST /api/v1/constant-parties/{constant_party}/invitations
```

При отправке можно добавить необязательное сообщение. Получатель видит его в карточке приглашения на странице **Мои КП**. Владелец приглашенного персонажа также получает системное уведомление.

### Статусы и фильтр

| Статус API | Подпись в интерфейсе | Значение |
|---|---|---|
| `pending` | Ожидает ответа | Приглашение еще не обработано |
| `accepted` | Принято | Персонаж вступил в КП |
| `declined` | Отклонено | Получатель отказался |
| `revoked` | Отозвано | Управляющий отменил приглашение |
| `expired` | Истекло | Приглашение стало недействительным, например после смены сервера |

На вкладке **Приглашения** доступен фильтр по этим статусам. По умолчанию показываются все статусы.

Получатель может принять или отклонить только приглашение своего персонажа:

```http
POST /api/v1/constant-parties/invitations/{invitation}/accept
POST /api/v1/constant-parties/invitations/{invitation}/decline
```

При принятии повторно проверяются сервер и отсутствие другого активного членства. Персонаж добавляется как обычный участник без права управления хранилищем. Вступление записывается в журнал и рассылается участникам КП.

При отказе отправителю приходит уведомление с ником персонажа и результатом. Pending-приглашение можно отозвать:

```http
POST /api/v1/constant-parties/{constant_party}/invitations/{invitation}/revoke
```

## Уведомления и изменения состава

Уведомления создаются при:

- отправке приглашения;
- принятии или отклонении приглашения;
- передаче лидерства;
- самостоятельном выходе;
- исключении лидером;
- автоматическом исключении после смены сервера;
- роспуске КП.

При вступлении, выходе и исключении уведомление содержит название КП, ник затронутого персонажа, действие и инициатора. Ушедшему или исключенному пользователю ссылка ведет на **Мои КП**, остальным участникам - на страницу КП.

## Смена и объединение серверов

### Смена сервера персонажа

| Сценарий | Поведение |
|---|---|
| Сервер меняет обычный участник | Персонаж исключается из КП, событие логируется, участники уведомляются |
| Сервер меняет лидер | Операция блокируется, пока персонаж является лидером |
| Персонаж с pending-приглашением сменил сервер | При принятии приглашение становится `expired` |

История выдач исключенного персонажа сохраняется.

### Административное объединение серверов

При объединении серверов КП переводится на целевой сервер вместе с персонажами. Сохраняются состав, лидер, права, приглашения, предметы, остатки, выдачи и журнал. Перенос больших объемов выполняется пакетно механизмом объединения серверов. Подробнее: [объединение серверов](server-merge.md).

## Хранилище КП

### Общие правила

Все участники могут просматривать хранилище и историю. Изменения доступны лидеру и участникам с `can_manage_storage=true`.

Добавление предмета и выдача предмета выполняются в отдельных модальных окнах. Существующий предмет можно переименовать и изменить его остаток.

Количество может быть ограниченным целым значением или `null`. При ограниченном остатке выдача атомарно проверяет доступное количество и уменьшает его. Недостаточный остаток возвращает `422` без частичного изменения данных.

```http
GET    /api/v1/constant-parties/{constant_party}/storage/context
GET    /api/v1/constant-parties/{constant_party}/storage/items
POST   /api/v1/constant-parties/{constant_party}/storage/items
PATCH  /api/v1/constant-parties/{constant_party}/storage/items/{item}
DELETE /api/v1/constant-parties/{constant_party}/storage/items/{item}
```

Предмет с существующей историей выдач удалить нельзя.

### Тиры предметов

Backend поддерживает категории с названием, цветом и порядком сортировки:

```http
GET    /api/v1/constant-parties/{constant_party}/storage/tiers
POST   /api/v1/constant-parties/{constant_party}/storage/tiers
PATCH  /api/v1/constant-parties/{constant_party}/storage/tiers/{tier}
DELETE /api/v1/constant-parties/{constant_party}/storage/tiers/{tier}
```

Тир, к которому привязаны предметы, удалить нельзя. На текущей странице КП отдельный интерфейс управления тирами не выведен.

### Выдачи и история участника

При выдаче обязательно указывается положительное целое количество. Дополнительно можно указать причину и дату выдачи.

```http
POST   /api/v1/constant-parties/{constant_party}/storage/grants
DELETE /api/v1/constant-parties/{constant_party}/storage/grants/{grant}
GET    /api/v1/constant-parties/{constant_party}/storage/items/{item}/grants
GET    /api/v1/constant-parties/{constant_party}/storage/characters/{character}/grants
GET    /api/v1/constant-parties/{constant_party}/storage/former-members
```

Отмена выдачи удаляет запись выдачи, возвращает количество в ограниченный остаток и создает отдельную запись журнала. Все операции изменения остатка выполняются в транзакции с блокировкой предмета.

История участника содержит предмет, количество, выдавшего персонажа, причину, дату и время. Дата отображается отдельной строкой, время - ниже приглушенным цветом.

## Журнал действий

Последняя вкладка **Логи** содержит неизменяемую историю:

- создания, удаления и переименования предмета;
- ручного изменения остатка;
- выдачи предмета и отмены выдачи;
- создания КП и вступления персонажа;
- самостоятельного выхода;
- исключения лидером или из-за смены сервера.

Запись хранит снимки названий предметов и персонажей, автора, получателя, старое и новое значение, количество, причину и служебные метаданные. Поэтому журнал остается читаемым после изменения связанных записей.

На страницу возвращается 50 действий. По умолчанию используется сортировка `desc`, от новых к старым. Доступны пагинация, сортировка и date range фильтр.

```http
GET /api/v1/constant-parties/{constant_party}/storage/logs?page=1&sort=desc
GET /api/v1/constant-parties/{constant_party}/storage/logs?date_from=2026-08-01&date_to=2026-08-31&sort=asc&page=1
```

`date_from` и `date_to` передаются в формате `YYYY-MM-DD`.

## Роспуск КП

Только лидер может нажать **Распустить КП**. Перед выполнением показывается окно подтверждения с предупреждением о необратимости.

```http
DELETE /api/v1/constant-parties/{constant_party}
```

В одной транзакции физически удаляются:

- активные и бывшие участники;
- приглашения;
- сообщения, receipts и socket-токены чата;
- тиры, предметы и остатки;
- выдачи и история участников;
- весь журнал КП;
- сама КП.

До удаления всем текущим участникам создается уведомление с названием КП и ником лидера-инициатора. Ссылка ведет на **Мои КП**. Восстановление удаленных данных не предусмотрено.

## Чат КП

> **Текущее состояние: отключен.** Код и данные сохранены для будущего использования.

### Поведение при отключении

Если `CONSTANT_PARTY_CHAT_ENABLED=0` или переменная отсутствует:

- вкладка **Чат** не отображается;
- frontend не запрашивает сообщения;
- компонент чата и `socket.io-client` не загружаются в браузер;
- Laravel chat API возвращает `404`;
- Laravel broadcaster не обращается к socket server;
- socket server не загружает модуль чата, не регистрирует комнаты и broadcast-маршруты.

Таблицы чата при этом не удаляются.

### Реализованная функциональность

После включения участники получают messenger-интерфейс с realtime-сообщениями, online presence и статусами доставки:

| Индикатор | Значение |
|---|---|
| Одна галочка | Сообщение сохранено |
| Две серые галочки | Доставлено всем исходным получателям |
| Две акцентные галочки | Прочитано всеми исходными получателями |

Для каждого получателя создается receipt. Доставка и прочтение обновляются идемпотентно пакетами до 100 сообщений. Прочтение отмечается только при активной вкладке чата и видимом окне. Несколько вкладок одного персонажа считаются одним пользователем онлайн.

```http
GET    /api/v1/constant-parties/{constant_party}/chat/messages
POST   /api/v1/constant-parties/{constant_party}/chat/messages
DELETE /api/v1/constant-parties/{constant_party}/chat/messages/{message}
POST   /api/v1/constant-parties/{constant_party}/chat/receipts/delivered
POST   /api/v1/constant-parties/{constant_party}/chat/receipts/read
POST   /api/v1/constant-parties/{constant_party}/chat/socket-token
POST   /api/v1/constant-party-chat/socket-auth
```

### Безопасность и включение

Клиент получает короткоживущий случайный токен, привязанный к пользователю, персонажу и КП. Socket server проверяет токен через Laravel и повторно проверяет активное членство перед входом в приватную комнату.

Служебные Laravel-to-socket broadcast-запросы защищены общим `SOCKET_SERVER_INTERNAL_TOKEN`. Это 256-битный секрет, который не передается браузеру. Для генерации:

```bash
openssl rand -hex 32
```

В корневом `.env`:

```dotenv
CONSTANT_PARTY_CHAT_ENABLED=1
SOCKET_SERVER_INTERNAL_TOKEN=<сгенерированные 64 hex-символа>
```

Одно значение `CONSTANT_PARTY_CHAT_ENABLED` передается Docker Compose в Laravel, frontend как `VITE_CONSTANT_PARTY_CHAT_ENABLED` и socket server. `SOCKET_SERVER_INTERNAL_TOKEN` должен быть одинаковым в PHP и socket-контейнере.

После изменения переменных:

```bash
docker compose up -d --force-recreate gg-php_8.4 gg-frontend socket-server-nodejs
docker compose exec gg-php_8.4 php artisan config:clear
docker compose exec gg-frontend npm run build
```

Для повторного отключения установить `CONSTANT_PARTY_CHAT_ENABLED=0` и пересоздать те же сервисы. Не следует генерировать разные internal-токены внутри отдельных контейнеров или pod.

## Текущие ограничения

| Ограничение | Возможное развитие |
|---|---|
| Расширенные роли КП отсутствуют | Добавить отдельные права помимо управления хранилищем |
| Поиск приглашений выполняется только по нику | Добавить фильтры класса, роли или уровня |
| Управление тирами доступно только через API | Добавить отдельный интерфейс на вкладке хранилища |
| Чат отключен | Включить единым feature flag после решения об использовании |
