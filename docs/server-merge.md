# Объединение серверов

## Назначение

Объединение переносит игровые сущности с одного или нескольких исходных серверов на выбранный целевой сервер. Операция выполняется фоновыми заданиями небольшими пачками, поэтому не зависит от тайм-аута HTTP-запроса и подходит для большого количества записей.

Исходные серверы сразу становятся неактивными, а все участвующие серверы получают `is_merging = true`. После успешного завершения исходные серверы получают `merged_into_server_id` и остаются в базе для истории.

## Запуск и статус

Запуск возвращает HTTP `202` и запись операции со статусом `pending`:

```http
POST /api/v1/games/{game}/localizations/{localization}/servers/merge
```

Получение последней операции локализации и конкретной операции:

```http
GET /api/v1/games/{game}/localizations/{localization}/server-merges/current
GET /api/v1/server-merges/{server_merge}
```

Ответ содержит `status`, `current_stage`, `total_records`, `processed_records`, `progress_percent`, разбивку `progress` по этапам и `error_message`.

Возможные статусы:

- `pending` — ожидает обработки очередью;
- `running` — выполняется;
- `completed` — успешно завершено;
- `failed` — все автоматические попытки исчерпаны, операцию можно продолжить.

Продолжение операции после ошибки:

```http
POST /api/v1/server-merges/{server_merge}/resume
```

## Переносимые данные

Этапы выполняются последовательно:

1. персонажи: обновляется `characters.server_id`;
2. гильдии: обновляется `guilds.server_id`;
3. конст пати: обновляется `constant_parties.server_id`;
4. группы серверов: связи `server_group_server` переносятся на целевой сервер без дублей;
5. финальная проверка и выключение исходных серверов.

Членство в гильдиях и конст пати не пересоздаётся и не удаляется.

## Большие объёмы и ошибки

Каждое задание переносит не более `SERVER_MERGE_CHUNK_SIZE` записей. Значение по умолчанию — `1000`.

```dotenv
SERVER_MERGE_CHUNK_SIZE=1000
```

Одна пачка и обновление её прогресса выполняются в общей транзакции. При ошибке текущая пачка откатывается целиком, но успешно завершённые ранее пачки остаются сохранёнными. Queue worker автоматически повторяет задание три раза. После исчерпания попыток операция переходит в `failed`.

При нажатии «Продолжить» обработка ищет записи, которые всё ещё ссылаются на исходные серверы, и начинает с первого незавершённого этапа. Уже перенесённые записи повторно не обрабатываются. Благодаря этому merge можно безопасно продолжить с сохранённого места.

Это намеренно не одна транзакция на весь merge: для миллионов записей общая транзакция долго удерживала бы блокировки и могла бы переполнить журнал транзакций.

Пока операция имеет статус `pending`, `running` или `failed`, участвующие серверы нельзя изменить или удалить, а создание и перенос персонажей, гильдий и конст пати на них блокируются. Это сохраняет стабильный набор переносимых данных до завершения или возобновления операции.

## Очередь

На окружении должен постоянно работать Laravel queue worker. Например:

```bash
php artisan queue:work --tries=3 --timeout=60
```

В production worker следует запускать под Supervisor, systemd или оркестратором контейнеров. Значение `DB_QUEUE_RETRY_AFTER` должно быть больше `timeout`; текущие значения `90` и `60` этому условию соответствуют.

После деплоя изменений необходимо выполнить миграции и перезапустить долгоживущие queue workers:

```bash
php artisan migrate
php artisan queue:restart
```

## Конст пати и банк

Merge является административным переносом всего сервера, поэтому участники не исключаются из конст пати. Лидер, участники и ожидающие приглашения сохраняются, так как персонажи исходных серверов также переносятся.

Банк не имеет собственной привязки к серверу. Уровни, предметы, история выдачи и права управления связаны через `constant_party_id`, поэтому сохраняются без изменений. Ссылки истории на добавивших, изменивших, выдавших и получивших предметы персонажей также остаются действительными.

При обычном индивидуальном переходе персонажа правила отличаются: участник исключается из КП, а переход лидера блокируется.

## Исправление старых данных

Если объединение выполнялось до добавления переноса КП, у неё мог остаться идентификатор неактивного исходного сервера:

```sql
UPDATE constant_parties cp
JOIN servers s ON s.id = cp.server_id
SET cp.server_id = s.merged_into_server_id
WHERE s.merged_into_server_id IS NOT NULL;
```

Перед исправлением рабочей базы требуется резервная копия и проверка затрагиваемой выборки.

## Проверка

Основные регрессионные тесты:

```bash
php artisan test tests/Feature/ServerMergeTest.php
php artisan test tests/Feature/ConstantPartyTest.php
```

`ServerMergeTest` проверяет перенос несколькими пачками, связи групп серверов, блокировку новых записей и продолжение с уже сохранённого прогресса.
